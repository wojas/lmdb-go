# gopeer: the Go peer of rlmdb's interop harness

`gopeer` speaks the peer command protocol of rlmdb's interop test bed
(rlmdb `interop/README.md`, "The peer command protocol"): the same
commands, options, output lines and exit codes as the C peer `cpeer`,
whose source (`interop/c/cpeer*.c`) it ports file by file to
lmdb-go's API. rlmdb's harness runs it as `Peer::External` next to C
LMDB 0.9 (`cpeer`), C LMDB 1.0 (`cpeer10`), rlmdb (`rpeer`) and C on
rlmdb (`cpeer_capi`), as separate processes on one environment.

```sh
cd tests
go build -o /tmp/gopeer ./gopeer                     # cgo and the port
/tmp/gopeer commands --impl cgo
/tmp/gopeer fill <env> mydb 1000 7 --dupsort --impl cgo
```

## One binary, two implementations

`--impl cgo|port` (an option like the others, anywhere after the command)
selects the implementation the protocol runs on:

* `cgo`: the pinned reference `../cgolmdb`: lmdb-go v1.9.4's Go code on C
  LMDB 0.9.36 plus ITS#10615, ITS#10642 and ITS#10643, the same code as
  LMDB 0.9.37 and as rlmdb's `cpeer`. A C 0.9 peer; it opens LMDB 0.9
  environments only (`--format 1.0` and `--pagesize` are usage errors, as
  for `cpeer`).
* `port` (the default): the Go implementation, both data formats
  (`--format` with lmdb-go v2's `Env.SetFormat`, `--pagesize` with
  `Env.SetPageSize`).

The peer is package `./cgo`, written against the cgo lmdb-go; `./port` is
the same code on the port, generated by `../gen-port.sh`
(`go generate ./gopeer`), except `impl.go`, which each side has by hand
for what differs: the implementation's name, the LMDB 1.0 calls, and
whether a reader can see C's meta race (below).

| file | C peer | commands |
|---|---|---|
| `cgo/peer.go` | `cpeer.c` | command line, exit codes, env open |
| `cgo/dataset.go` | `dataset.c` | the deterministic data set |
| `cgo/data.go` | `cpeer_data.c` | `fill`, `verify`, `delete`, `drop`, `dump` |
| `cgo/loops.go` | `cpeer_loops.c` | `hold-reader`, `hold-env`, `hold-writer`, `writer-loop`, `reader-loop` |
| `cgo/misc.go` | `cpeer_misc.c` | `create`, `stat`, `readers`, `reader-check`, `copy`, `nested-test`, `gen` |
| `cgo/pagewalk.go` | `cpeer_pagewalk.c` | `check-freelist` (format from meta page 0, as rpeer) |

## What lmdb-go's API cannot express

Every command of the protocol is implemented except `formats-loop`, which
only rpeer has (exit 4, as for `cpeer`). Where lmdb-go's API differs from
C's, gopeer does this:

* **`mdb_del(key, NULL)` on a DUPSORT DB** (`delete`, every other whole
  key). lmdb-go v1's `Txn.Del(dbi, key, nil)` passes an empty value
  instead of `NULL`, so C looks for that value and fails (`MDB_NOTFOUND`,
  or `MDB_BAD_VALSIZE` for a key with a sub-page or sub-DB). With `--impl
  cgo` gopeer deletes such keys with `MDB_SET` +
  `mdb_cursor_del(MDB_NODUPDATA)`, which is what `mdb_del` does
  internally (same tree changes), and prints one `NOT-IMPLEMENTED` line,
  which the harness reports as `SKIPPED partly`. The port's
  `Txn.Del(dbi, key, nil)` is `mdb_del` with `NULL` (`delNullData` in
  `impl.go`).
* **`MDB_NOTLS`**: lmdb-go opens every environment with it, so `--notls`
  changes nothing and read transactions always behave like `MDB_NOTLS`
  ones (as rpeer's do).
* **`MDB_GET_MULTIPLE` on a key with one value**: C succeeds without
  touching `*data`, which still holds `MDB_SET`'s value; lmdb-go clears
  its value after every call and returns an empty slice. `verify` uses
  `MDB_SET`'s value then, as C's caller sees it.
* **`RawRead`**: gopeer keeps lmdb-go's default (values copied out of the
  map). With `RawRead` true, lmdb-go v1's `Cursor.Get` panics (nil
  pointer) after `MDB_FIRST_DUP` and `MDB_LAST_DUP`, for which C leaves
  the key unset.
* **Reader meta race** (rlmdb `KNOWN_C_BUGS.md` #31): on `cgo`,
  `reader-loop` tolerates a step back of `#commits` with the signature of
  C's race and counts it in `meta_races`, as `cpeer` does; on `port`, as
  on rlmdb, any step back fails.
* Error messages are `gopeer: <call> failed: <code> <strerror>`, with
  system errors capitalised as C's `strerror` (the harness looks for
  "Function not implemented").

## Running rlmdb's interop tests with gopeer

rlmdb's interop crate (`Peer::External`, in rlmdb's main since `0f902b4`)
finds gopeer through
`INTEROP_PEER` (its path), `INTEROP_PEER_ARGS` (`--impl cgo` or `--impl
port`) and `INTEROP_PEER_NAME` (`Go`); without `INTEROP_PEER` the tests
are skipped.
In the rlmdb checkout:

```sh
INTEROP_PEER=/tmp/gopeer INTEROP_PEER_ARGS='--impl cgo' INTEROP_PEER_NAME=Go \
    cargo test -p rlmdb-interop --test external_peer --test external_pairs --test external_pairs10
```

On Linux, rlmdb's `scripts/linux-test.sh` runs cargo in a
`rust:1-bookworm` container that sees only the rlmdb checkout (read-only
in the VM) and passes no environment. Build a Linux gopeer in this
repository's Debian golang container (same glibc), write it into the
rlmdb checkout through stdout, and hand the variables to the tests with
cargo's `--config env`:

```sh
# in this checkout
mkdir -p <rlmdb>/interop/external
scripts/linux-test.sh sh -c 'cd tests && go build -o /tmp/gopeer ./gopeer >&2 && cat /tmp/gopeer' \
    > <rlmdb>/interop/external/gopeer-linux && chmod +x <rlmdb>/interop/external/gopeer-linux
# in the rlmdb checkout (interop/external is git-ignored there)
scripts/linux-test.sh test -p rlmdb-interop --test external_peer --test external_pairs \
    --config 'env.INTEROP_PEER="/work/interop/external/gopeer-linux"' \
    --config 'env.INTEROP_PEER_ARGS="--impl cgo"' --config 'env.INTEROP_PEER_NAME="Go"'
```

gopeer builds and runs on musl too:
`LINUX_TEST_IMAGE=golang:1.25-alpine scripts/linux-test.sh sh -c 'apk add -q
build-base && cd tests && go build -o /tmp/gopeer ./gopeer >&2 && cat
/tmp/gopeer'`. glibc and musl lock files differ (on arm64
`pthread_mutex_t` is 48 bytes with glibc, 40 with musl), so a musl gopeer
must meet C peers built against musl. The matrix runs in an image derived
from `rust:1-alpine` with `build-base` (rlmdb's `linux-test.sh`
runs `cargo` directly), on a target volume of its own (so that glibc and
musl builds do not overwrite each other), with the musl gopeer streamed
into the rlmdb checkout as above; rlmdb's `build.rs` builds `cpeer` and
the C tools against musl there, from the C sources rlmdb vendors
(`tests/lmdb-c`), and every pair also runs reader loops of rlmdb's peers
(`rpeer`, `cpeer_capi`) on musl's mutexes:

```sh
printf 'FROM rust:1-alpine\nRUN apk add -q build-base\n' | docker build -q -t rlmdb-interop-musl -
docker run --rm -i --tmpfs /tmp:exec,size=4g -v <rlmdb>:/work \
    -v lmdb-rs-target-musl:/work/target -v lmdb-rs-cargo-registry:/usr/local/cargo/registry \
    -w /work -e INTEROP_PEER=/work/interop/external/gopeer-linux -e INTEROP_PEER_ARGS='--impl port' \
    -e INTEROP_PEER_NAME=Go rlmdb-interop-musl \
    cargo test -p rlmdb-interop --test external_peer --test external_pairs --test external_pairs10
```

### Results with `--impl port` (the Go implementation)

Every Go test of rlmdb's interop matrix passes: `external_pairs` (165
tests: every scenario with Go and C 0.9, Go and Rust both ways, and Go on
both sides, on LMDB 0.9 environments), `external_pairs10` (231: Go with
C 1.0, Rust and C on Rust both ways, and Go on both sides, on LMDB 1.0
environments) and `external_peer` (5, among them `four_writers` and
`four_writers10`: writer and reader loops of C, Rust, C on Rust and Go
at once). That covers
writers of all implementations excluding each other, readers seeing each
other in the reader table, MVCC, killed writers (robust mutex recovery on
Linux), copies, and C's page audit and page-by-page comparison of what Go
wrote. `delete` needs no workaround.

| | `external_pairs` | `external_pairs10` | `external_peer` |
|---|---:|---:|---:|
| macOS 15 (arm64) | 165 / 165 | 231 / 231 | 5 / 5 |
| Linux arm64, glibc (Debian bookworm) | 165 / 165 | 231 / 231 | 5 / 5 |
| Linux arm64, musl (Alpine) | 165 / 165 | 231 / 231 | 5 / 5 |
| Linux x86-64, glibc (Debian bookworm, under Rosetta) | 165 / 165 | 231 / 231 | 5 / 5 |

The macOS and Linux arm64 rows are from 2026-11-02, with rlmdb's main at
`0f902b4`; the x86-64 row is from the final validation (2026-11-01), with
rlmdb's main after its restructuring (with `Peer::External` on top; the
scenarios include 1- to 3-byte `MDB_DUPFIXED` data sets; the Go peer's data
set and page audit follow them). The x86-64 row ran in an x86-64 container under
Rosetta (`--platform linux/amd64`, `rust:1-bookworm`, the gopeer built
in the same platform's golang container, a target volume of its own);
there `external_pairs10` and `external_peer` ran with
`-- --test-threads=1`: with parallel tests the harness process itself
stopped twice after 93 and 166 tests, in different scenarios, with every
thread of the test binary waiting in the kernel on a priority-inheritance
futex (which neither C LMDB, rlmdb nor the harness uses) and no peer
process running, which points at the emulator rather than at a peer.

### Results with `--impl cgo` (the reference)

Every test passes: gopeer knows the same commands as `cpeer`, `gen` is
byte-identical, and `verify`, `dump --all`, `stat` and `check-freelist`
print exactly what `cpeer` prints on an environment C wrote; writer loops
of C, Rust, C on Rust and Go at once keep `#commits` exact. That covers
locking, the reader table, MVCC, killed writers (robust mutex recovery on
Linux), copies, DUPSORT page counts and `same_writes_same_pages`, with
rlmdb's main at `0f902b4` (2026-11-02). `delete` runs with the workaround
above, so the harness reports it as `SKIPPED partly`.

| | `external_pairs` | `external_peer` |
|---|---:|---:|
| macOS 15 (arm64) | 165 / 165 | 5 / 5 |
| Linux arm64, glibc (Debian bookworm) | 165 / 165 | 5 / 5 |
| Linux arm64, musl (Alpine) | 165 / 165 | 5 / 5 |

The 1.0 pairs (`external_pairs10`) and `four_writers10` are skipped: the

### The released lmdb-go v1.9.4 (C LMDB 0.9.35)

A peer on the released v1.9.4's C code does not pass the DUPSORT checks,
because of the C version, not the peer. C 0.9.35 is from before ITS#9388
(0.9.36: a DUPSORT DB's `md_branch_pages`/`md_leaf_pages` include its
sub-DBs' pages) and ITS#10643 (0.9.37: page counts when deleting DUPSORT
records). `cpeer` and rlmdb follow the newer accounting, so their
`check-freelist` rejects DUPSORT DBs with sub-DBs that 0.9.35 wrote (and
counts that went negative where both versions wrote one DB), and
`same_writes_same_pages` finds the main DB's record of such a DB
different. Locking, the reader table, MVCC, killed writers, copies and all
data checks pass. Measured on 2026-11-02 with rlmdb's main at `0f902b4`,
with this peer built on that C code:

| | passed | failed: DUPSORT page counts | failed: `same_writes_same_pages` |
|---|---:|---:|---:|
| macOS 15 (arm64) | 127 | 33 | 5 |
| Linux arm64, glibc (Debian bookworm) | 125 | 35 | 5 |
